# Практическая работа №2 — Телеметрия UDP-протокола (RTT/jitter/loss)

## Задание
Спроектировать и реализовать подсистему телеметрии UDP-протокола: измерять RTT, оценивать сглаженный RTT, джиттер и долю потерь, корректно обрабатывать недействительные, дублирующиеся и запоздалые ответы.

Шаблон: https://gitverse.ru/univ-mirea-iit/course-multiplayer/content/master/pr2-latency-template

## Реализация

### Структура решения (`src/`)
```
LatencyTelemetry.sln
├── Protocol/    — PING/PONG: формат пакета, кодек, исключение для битых пакетов
├── Telemetry/   — расчёт RTT/SRTT/джиттера/потерь, ничего не знает о сети
├── Transport/   — тонкая обёртка над UDP-сокетом, ничего не знает о формате пакетов
├── PingServer/  — консольный сервер (+ имитация потерь/дублей/задержек для демонстрации)
├── PingClient/  — консольный клиент, ведёт docs/latency_samples.csv
└── Tests/       — xUnit: сериализация, статистика, обработка ошибок (21 тест)
```
Модули **Protocol**, **Telemetry** и **Transport** не смешивают сетевой ввод, сериализацию и расчёт метрик: `Telemetry.LatencyTracker` принимает только номера последовательности и временные метки (никаких сокетов), `Transport.UdpTransport` передаёт только байты (не знает про PING/PONG), `Protocol.PacketCodec` только сериализует/валидирует (не считает никаких метрик).

### Формат пакета
`[Type:1][SequenceNumber:4][ClientTimestampTicks:8]`, big-endian, 13 байт. PONG эхом возвращает клиентскую метку времени — RTT считается по часам клиента, синхронизация часов между машинами не нужна.

### Телеметрия (`Telemetry/`)
- **SRTT** — RFC 6298 (тот же алгоритм, что TCP использует для расчёта таймаута ретрансмиссии): `SRTT=(1-α)SRTT+αR`, `RTTVAR=(1-β)RTTVAR+β|SRTT-R|`, α=1/8, β=1/4.
- **Джиттер** — RFC 3550 §6.4.1: `J = J + (|D|-J)/16`, где `D` — разница соседних RTT.
- **Потери/дубли/опоздания** — `LatencyTracker`: запрос считается потерянным, если ответ не пришёл до вызова `Tick()` спустя заданный таймаут после отправки; более поздний ответ на уже потерянный запрос помечается `Late` и **не** уменьшает долю потерь (операционно он опоздал, даже если сеть его не потеряла); повторный ответ на уже подтверждённый запрос — `Duplicate`; ответ на номер, который не отправлялся — `Unknown`.

### Имитация сетевых искажений (`PingServer`)
На localhost RTT≈0 и потерь нет — телеметрии нечего было бы ловить. Поэтому сервер сознательно вносит: 5% потерь, 5% дублирования PONG, случайную базовую задержку 5–40 мс и 8%-й «всплеск» задержки 200–400 мс (заведомо больше таймаута клиента — порождает `Late`). Подробности и обоснование — [Experiment_Config.md](docs/Experiment_Config.md).

## Как запустить

```bash
cd src
dotnet build
dotnet test
```

В одном терминале: `dotnet run --project PingServer`
В другом: `dotnet run --project PingClient` (отправит 200 PING, ~25 сек, запишет `docs/latency_samples.csv`)

## Тесты (21, все проходят)
- **Protocol** — round-trip сериализации, фиксированный размер пакета, обрезанный/удлинённый/пустой пакет и неизвестный тип → `MalformedPacketException`.
- **Telemetry** — формулы SRTT/джиттера сверены с ручным расчётом; `LatencyTracker` — сценарии OnTime/Duplicate/Unknown/Lost/Late и корректность доли потерь на смешанном наборе исходов.
