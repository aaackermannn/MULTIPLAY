# Практическая работа №1 — UDP-сервер и UDP-клиент

## Задание
Разработать консольное приложение на C#, состоящее из двух программ:
1. **UDP-сервер** — принимает пакеты от клиентов, обрабатывает команды (`MOVEMENT`, `SHOOT`) и отправляет обновлённое состояние.
2. **UDP-клиент** — отправляет команды на сервер и получает ответы.

## Реализация

### Структура решения (`src/`)
```
UdpMultiplayer.sln
├── GameProtocol/   — библиотека протокола (заголовок пакета, payload'ы, кодек)
├── GameServer/     — консольный UDP-сервер
└── GameClient/     — консольный UDP-клиент
```

### Формат пакета
`[PacketHeader: 7 байт][Payload: N байт][CRC32: 4 байта]`, все числовые поля — **network byte order (big-endian)**, как рекомендует Beej's Guide to Network Programming.

| Поле         | Размер  | Описание                                   |
|--------------|---------|---------------------------------------------|
| Command      | 1 байт  | `Movement=1`, `Shoot=2`, `StateAck=3`       |
| SequenceNumber | 4 байта | Порядковый номер пакета                   |
| PayloadSize  | 2 байта | Размер полезной нагрузки в байтах (без CRC)|

Полезные нагрузки:
- **MovementPayload** (8 байт): `float X, float Y` — новая позиция игрока.
- **ShootPayload** (4 байта): `float AngleDegrees` — угол направления выстрела.
- **StateAckPayload** (12 байт): `uint AckedSequenceNumber, float X, float Y` — подтверждение сервера с актуальным состоянием.

**Доп. задание — контрольная сумма (CRC32):** каждый пакет завершается 4-байтным CRC-32 (полином `0xEDB88320`, как в Ethernet/ZIP), посчитанным по заголовку+payload. Получатель пересчитывает CRC и отбрасывает пакет при несовпадении — UDP сам целостность данных не гарантирует, а более простой "испорченный размер payload" такую подмену данных внутри payload не поймал бы. Реализация: [`GameProtocol/Crc32.cs`](src/GameProtocol/Crc32.cs).

**Почему без `#pragma pack`/бинарного маппинга структур:** вместо прямого наложения C-структуры на массив байт (источник проблем с выравниванием, о которых предупреждает cppreference) поля пишутся и читаются explicit-методами `WriteTo`/`ReadFrom` через `BinaryPrimitives` в заранее рассчитанные смещения — платформонезависимо и без риска padding-байтов.

### Логика сервера (`GameServer/Program.cs`)
- Слушает UDP-порт 5055.
- Хранит позицию каждого клиента в `Dictionary<string, PlayerPosition>`, ключ — адрес клиента (`IP:port`).
- При `MOVEMENT` — обновляет позицию, логирует и отправляет `StateAck` с новыми координатами.
- При `SHOOT` — логирует выстрел с текущей позицией игрока, отправляет `StateAck`.
- Некорректные пакеты (несовпадение заявленного и фактического размера payload) отбрасываются с записью в лог, сервер не падает.
- Ведёт лог всех полученных команд в `server.log` (дата/время, тип команды, клиент, параметры) и дублирует в консоль.

### Логика клиента (`GameClient/Program.cs`)
- Подключается к серверу `127.0.0.1:5055`.
- Раз в секунду отправляет команду: 3 из 4 раз — `MOVEMENT` (случайное смещение позиции), каждый 4-й раз — `SHOOT` (случайный угол).
- Выводит в консоль отправленную команду и ответ сервера (или таймаут, если ответ не пришёл за 2 секунды).

## Как запустить

```bash
cd src
dotnet build
```

В одном терминале:
```bash
dotnet run --project GameServer
```

В другом терминале:
```bash
dotnet run --project GameClient
```

## Связь с дипломным проектом
Протокол и структура сервера спроектированы как черновой прототип боевой/рейдовой подсистемы будущей AR-игры (аналог Pokemon Go): `MOVEMENT` — синхронизация позиции игрока в момент боя, `SHOOT` — применение способности/атаки. В дальнейшем (ПР2, курсовая) этот же протокол расширяется телеметрией задержки и серверной валидацией координат (защита от GPS-спуфинга).
